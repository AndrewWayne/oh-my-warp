# 需求:面向 pane 的可点击通知(Pane-Focus Notifications)

- 日期:2026-07-20
- 状态:需求草案(待维护者对齐)
- 关联:`cli_agent_sessions`(agent 会话感知)、`[tui]`/`[desktop]` 设置体系、`root_view::focus_pane`

## 一句话目标

让 omw 里**任意 pane** 的程序(尤其 AI agent)在"完成一轮 / 需要你决定"时弹出系统通知,**点击通知直接聚焦到发出它的那个标签(tab)和 pane**;整套行为可在 omw 设置里配置,声音/文案可自定义且易扩展。

## 背景与动机

- omw 定位是 AI 终端 / 本地多 agent 编排,用户常同时在多个标签里挂 codex / claude / 自定义 agent。
- 现状痛点:
  - agent "完成一轮" 或 "卡住等你批准" 时,omw 不发系统通知,只能靠外部工具(terminal-notifier 等)。
  - 而外部通知点击后**只能把 omw 拉到前台,无法定位到具体标签/pane**——因为 omw 目前**没有 OSC 9/777 通知支持,也没有对外的"聚焦某 pane"入口**(已核实源码)。
- 结果:用户得在多个标签间反复轮询,"谁好了 / 谁在等我" 全靠肉眼扫。

## 改完之后能达成的效果(验收标准 · 用户视角)

> 这一节是核心:描述"做完之后用户能得到什么",作为验收依据。

1. **会弹通知**:pane 里的程序发出通知请求时,系统弹出原生通知;标题/正文能带来源信息(项目名 / 标签名等)。
2. **点击直达**:点击通知 → omw 前置 → **自动切到发出该通知的标签 → 并聚焦其 pane**。即便当时停在别的标签、别的窗口,也能精确回到"发通知的那个对话",**多 agent 并行时点哪条回哪条,不误跳**。
3. **任意工具可用**:不绑定某个 agent。任何程序只要往终端写标准通知转义(OSC 9 / OSC 777)就能触发——codex、claude、脚本、普通长命令皆可。
4. **覆盖两类关键事件**:
   - **完成 / 停下等你**:agent 一轮结束、把控制权交回给你。
   - **需要你回答 / 批准才能继续**:权限确认、需要你做选择的决策点。
5. **可在 omw 设置里配置**:设置面板有独立的"通知"区,至少能:
   - 总开关;按事件类型分别开关。**默认:整个功能开启。**
   - "何时弹"策略:**默认"始终弹"**(事件驱动,不看你在不在场);另提供可选项"当发通知的 pane 已在前台时不弹",**默认关**。
   - 是否"点击聚焦",以及聚焦行为(抬窗口 / 选标签 / 选 pane)。
6. **声音等可自定义、易扩展**(用户明确要求):
   - 通知声音可选:系统内置音 + **用户自定义音频文件**;可**按事件类型配不同声音**(如"完成"和"等你"不同提示音)。
   - 通知标题/正文支持**模板变量**(项目名、pane 标题、耗时、来源工具等)。
   - 架构上预留扩展点:新增事件类型 / 新增通知渠道(未来转发手机、Tailscale) / 按 pane 或 profile 覆盖,**都不需要伤筋动骨**。
7. **不打扰**:尊重系统"勿扰/专注"模式;同一 pane 的连续通知可**合并**(不刷屏);支持去重 / 节流。
8. **稳定不误伤**:功能关闭时行为与现状完全一致;转义解析健壮,绝不影响正常终端输出与性能。

## 范围

**本期做(In)**
- OSC 9 / OSC 777 通知转义解析 → 原生系统通知(通用地基:任何程序都能触发)。
- 点击通知 → 聚焦"发出该转义的 pane"(标签 + pane)。
- **原生识别 agent turn**:omw 直接识别 codex/claude 会话的 "turn 完成 / 等待批准",**不依赖程序主动发转义**就能弹可点击通知,复用 `cli_agent_sessions`(用户要求纳入本期)。
- omw 设置面板中的通知配置区(TOML 键 + 设置 UI)。
- 声音(内置 + 自定义文件)、文案模板、事件开关、"何时弹"策略。
- macOS 优先;Linux 留出通知层抽象接口。

> 建议按阶段交付(同一设计下):**P1 = OSC 9/777 通用通知 + 点击聚焦 + 设置/声音**;**P2 = 原生 agent turn 识别**(复用 P1 的通知与聚焦地基,只是触发源从"程序发转义"扩展到"omw 自己判定")。两阶段共用同一套通知/聚焦/配置代码。

**本期不做(Out · 记为后续)**
- 手机 / Tailscale 通知转发(通知渠道 trait 要为它预留)。
- Windows。

## 关键约束 / 设计取向(给实现者的方向,非拍死)

- **走标准转义**:以 OSC 9 为主,兼容 OSC 777(rxvt 风格),对齐 iTerm2 / kitty / WezTerm 的既有行为,便于生态里现成工具直接复用。
- **聚焦语义**:窗口 raise + 选中 tab + 选中 pane;若该 pane 已在前台,则只提示不跳(避免打断)。复用现有 `focus_pane` locator 能力。
- **配置一致性**:纳入 omw 现有 settings 体系,键命名与 `[tui]` / `[desktop]` / `appearance.panes` 等保持风格一致;设置 UI 落在合适的分区。
- **平台抽象**:通知投递做成接口,macOS 用系统原生通知,Linux 走 notify/dbus,渠道以 trait 形式可插拔(为 phase 2 的转发渠道铺路)。
- **扩展点显式化**:事件类型用枚举;声音解析支持"名字或文件路径";文案用模板变量表;通知渠道用 trait。让"加一种事件 / 加一个声音 / 加一个渠道"是填空题,不是改架构。

## 已定决策

- 功能**默认开启**。
- 默认**始终弹**(事件驱动);"pane 在前台就不弹"为可选、默认关。
- **原生识别 agent turn 纳入本期**(建议作为 P2 阶段,与 P1 共用通知/聚焦/配置地基)。

### 维护者已拍板(2026-07-20,基于集群调研)

- **重大发现**:OSC 9/777 解析 → 桌面通知 → 点击聚焦发起 pane 的全链路在本 fork **已存在**(`FeatureFlag::PluggableNotifications`、`Event/ModelEvent::PluggableNotification`),只是被 feature flag 双重关闭。本特性主体是**"解门控 + 补策略"**,非从零开发。设计/计划见同目录 `*-design.md` 与 plans 下 `*-plan.md`。
- **事件分类**:P1 只做**单一"通用通知"**,不动解析/handler 层;"完成 vs 等批准"的区分交给 **P2 的原生 agent 识别(CLIAgentEventType)**。
- **默认开的实现**:新增独立开关 **`is_escape_sequence_enabled`(默认 true)+ 解门控**,不改现有 `mode`(Unset 默认)、不碰 `terminal/view.rs:14335` 的 banner 逻辑。
- **自定义声音**:走 **`~/Library/Sounds` + 按名引用**(把用户选的音频拷入该目录再以名字引用),纯上层、不改打包。已实测该目录下自定义名可被通知声音识别(`osascript` 与 `terminal-notifier` 均接受)。
- **实施排序**:**MS0 解门控(阻塞一切)→ P1(MS1-5:精确聚焦/默认始终弹+前台抑制/事件与声音/去重节流勿扰/设置页)→ P2(MS6:原生 agent turn 识别)**。
